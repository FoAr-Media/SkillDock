# Implementation plan — independent review (v0.1.0 → v0.1.1)

Method: read every doc, then the source (≈2.8k LOC), reproduced each suspected defect with a failing test **before** changing code, and fixed with minimal diffs in the existing modules. No module was rewritten. Reproductions live in `packages/core/test/review.test.ts` and `tests/unit/boundary.test.ts`; end-to-end coverage in the "REVIEW" steps of `tests/e2e/app.e2e.mjs`.

## Verdict on the renderer / preload / main separation
**Holds.** Verified by code and by `tests/unit/boundary.test.ts` + e2e:
- Renderer imports only `react`, relative modules, CSS (no `electron`, Node, or `@skilldock/core`, not even types). Bundle contains no zod/MCP SDK/sqlite.
- Preload exposes exactly one function (`invoke`) behind a channel-name pattern; raw `ipcRenderer` is never exposed.
- Main is the only enforcement point: unknown channels don't exist, every payload is zod-parsed, sender must be our window's main frame, renderer passes ids not paths (config files and skills re-resolved server-side).
- `sandbox`, `contextIsolation`, `!nodeIntegration`, `webSecurity`, denied `window.open`, blocked navigation, denied permission requests.
**Weakness found and fixed:** the "approval" for starting processes was a boolean the *renderer* supplied (see F4). Accepted design choice: preload's `invoke` is generic rather than a per-channel allow-list; enforcement is in main (documented in DECISIONS).

## Findings (priority · status · evidence)
### P0 — data loss / security (all FIXED, each with a failing-then-passing test)
| # | Finding | Fix |
|---|---|---|
| F1 | **Studio save destroyed data.** It `rm -rf`'d the skill dir and rewrote only the editor's text files: PNGs were corrupted (UTF-8 round-trip), files ≥512 KB silently deleted. Same for "Export" of installed skills. | Save never wipes the directory; only changed text files are written, deletions only for files the user explicitly removed; binary/large files are not loaded and are untouched; installed-skill export is a byte-for-byte copy (`exportSkillDir`). |
| F2 | **Config writes replaced symlinked files** (dotfile-managed `settings.json`), and backups of a symlink recorded only the link, so rollback could not restore content. | `updateJson`/`saveText`/`atomicWrite` resolve the real path first; backup and write target the real file; link preserved. |
| F3 | **CLI option injection**: `claude plugin enable --help` really executed; `runWithClaude` accepted a prompt like `--dangerously-skip-permissions`; marketplace source `--x/y` allowed. | IDs/sources must start alphanumeric; prompts starting with `-` rejected. |
| F4 | **Trust-model hole**: `approved:true` was sent by the renderer, so a compromised renderer could start any process (`mcp:testDraft`), spend usage (`studio:runClaude`) or run plugin commands. | Main shows a native system dialog (with the exact command) for `mcp:test`, `mcp:testDraft`, `studio:runClaude`, `plugins:action`, `plugins:addMarketplace`; schema requires literal `approved:true`; e2e proves denial blocks execution (a would-be `pwned` file is never created). |
| F5 | **Preview read through symlinks** (`skills:file` used `stat`), exposing any file a skill-dir symlink points at. | `readSkillFile`: lstat, reject symlinks, realpath must stay inside the skill root. |
| F6 | **Frontmatter injection** in agent creation via newlines in `tools`/`model`. | Single-line regexes. |
| F7 | **GitHub owner/repo `..`** accepted, letting a crafted source reach other API paths with the token attached. | Dots-only names rejected. |

| # | Finding | Status |
|---|---|---|
| F15 | **`.mcp.json` approval state ignored** (UI implied "configured = active"). | **FIXED.** Each server now carries a configuration state mirroring `claude mcp list`: `approved / pending / rejected / disabled / managed / not-required`, with the reason. Rules implemented from the docs: user + managed settings approvals always count; project shared/local settings approvals count only after workspace trust (`projects[path].hasTrustDialogAccepted`); `disabledMcpjsonServers` in any file rejects and beats approval; `enableAllProjectMcpServers`; per-project `disabledMcpServers` (`~/.claude.json`); same name in several scopes → local > project > user, entry used whole (shown as "overridden"). Per-project `enabledMcpjsonServers` arrays that exist in real `~/.claude.json` files but are not in the current docs are honoured only as `observedOnly` and labelled. The app never approves servers (approval stays in Claude Code). Dashboard shows "MCP pending approval". Also fixed a latent bug found on the way: `~/.claude.json` project keys are now matched by **realpath** (macOS `/var` vs `/private/var`, symlinked folders) for reads and writes; before, trust/disabled flags and local servers could silently miss and a write could create a duplicate key. |
| F16 | **Same-name skills not flagged.** | **FIXED.** `analyzeSkillNames` implements the documented table: enterprise › personal › project; a skill beats a `.claude/commands` file; a skill replaces a built-in command (not its aliases; built-in list is curated); `ship`/`ship-local`/`steward` are not loaded; plugin skills are namespaced and never conflict; skills of different projects never interact; two skills of the same level with one name are reported as `duplicate` (docs do not say which runs). Surfaced in My Skills (badges, "Name conflicts only" filter, "Name resolution" section), in the **install plan** before anything is written, and on the dashboard. Not modelled: enterprise-managed skills, nested/added-directory skills, claude.ai synced skills. |
| F17 | Unconfirmed formats. | **Partly resolved.** `skillOverrides` IS documented (values `on / name-only / user-invocable-only / off`; any settings file; `/skills` menu writes `.claude/settings.local.json`) — our "Disable" writes `"off"` correctly, but we only read the user file. Still unconfirmed: `installed_plugins.json` layout (observed only) and the managed file paths. |
| F18 | Hooks only read from settings files. | **FIXED.** Rules from the official [hooks](https://code.claude.com/docs/en/hooks.md), [plugin components](https://code.claude.com/docs/en/plugins/components.md), [manifest](https://code.claude.com/docs/en/plugins/manifest-reference.md) and [settings-reference](https://code.claude.com/docs/en/settings-reference.md) pages. `listHooks` now returns a report covering **all documented sources**: user/project/local settings; managed `managed-settings.json` **and `managed-settings.d/*.json`**; plugin `hooks/hooks.json` plus the manifest `hooks` key (path, inline object, or array — both load); skill, custom-command and subagent frontmatter. All **five handler types** are understood (`command` incl. exec form vs shell form, `http`, `mcp_tool`, `prompt`, `agent`); the old code read only `command ?? prompt ?? url`. Each hook gets a configuration status with a reason: `blocked` (`allowManagedHooksOnly`, honouring force-enabled plugins; `strictPluginOnlyCustomization` true/`["hooks"]`), `disabled` (`disableAllHooks` with local › project › user precedence; managed hooks unaffected from below), `inactive` (plugin disabled), `trust-gated` (project hook in a folder without workspace trust: held back interactively but **run by `claude -p`**), `on-demand` (frontmatter), else `configured`. Risk flags are now type-aware (http → destination host, plain HTTP, `allowedEnvVars` passed into headers; prompt/agent → usage + tools) and **scripts referenced via `${CLAUDE_PLUGIN_ROOT}` / `${CLAUDE_PROJECT_DIR}` are read (contained, ≤256 KB, no symlinks) and scanned**, since the command string alone says nothing about a script's behaviour. A plugin's root-level `hooks.json` is deliberately NOT listed (not a documented location; an earlier survey of installed plugins found one that Claude does not load). Side fix: `managed-settings.d/` drop-ins were also missing from inheritance, MCP approval and the config-file list; all now use one shared merge (single values: later wins; lists combine) and drop-ins show up read-only. |
| F19 | Skill `name` vs directory. | **Resolved by docs:** the frontmatter `name` sets the command and the directory name also invokes the skill; plugin skills are `/plugin:name`. UI now shows both invocation names and the "inferred" wording was replaced by "per Claude Code docs". |

New open items found while researching: (a) `skillOverrides` is read only from user settings, but it may also live in project/local settings (and `name-only`/`user-invocable-only` values are shown as enabled); (b) approvals in an untracked `settings.local.json` are assumed untracked (the docs say Claude runs `git` to check); (c) `claude -p`, SDK and cloud sessions load project servers without asking — surfaced in the Pending reason text but not modelled per mode; (d) hooks: not modelled — `/hooks`-menu runtime state, the 1,024-hook per-source limit, dedupe of identical handlers across files, `disableAllHooks` per-session `--settings`, hook-script scanning beyond the two documented path variables, SDK in-process hooks, mods (`modules` in `hooks/hooks.json`), cloud/self-hosted seeded hooks.

### P3 — architecture / dependencies (OPEN, accepted with rationale)
- **`node:sqlite` is experimental** (prints a warning; API may change). Chosen to avoid a native-module rebuild. Mitigation: all SQL isolated in `store.ts` + a few `store.run` calls; swap to better-sqlite3 if Node/Electron changes it. Spec's Drizzle ORM not adopted (YAGNI).
- Unnecessary dependencies: none in source; the packaging bloat (F20) is fixed. Runtime: yaml, zod, diff, MCP SDK (all used); `zod` is declared in both packages (desktop uses it in handlers). Dev-only: playwright-core, axe-core, electron-builder. Renderer bundle is plain React 19 (776 kB min, not a leak).
- `handlers.ts` (≈300 lines) is large but flat and uniform; splitting would be churn without benefit now. Split when a domain gains non-trivial logic.
- Spec stack deviations (Tailwind/shadcn/Zustand/TanStack/RHF/Monaco) remain deliberate (DECISIONS #2, #8).
- Backups are unbounded (no retention) and may contain secrets (0600, not encrypted). Add retention + optional encryption.
- Windows/Linux never executed; `open -a Terminal` is macOS-only; no code signing/notarization; org-catalog signatures displayed not verified.
- `skills:list` re-scans disk per call (fine at ~170 skills; add caching/watchers beyond ~1k).
- Studio "Export" of an *unsaved/in-editor* skill is text-only (documented); use My Skills → Export for lossless.
